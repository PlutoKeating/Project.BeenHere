# Project.BeenHere · 架构方案（阶段 2）

> **你不需要重要，才值得被记录。**
>
> 本文从项目灵魂出发，以架构师的视角，把「见证一个人曾经来过」拆解成一套可行的开发方案。
> 本阶段**不涉及具体技术栈、部署、存储与实现细节**——那些统一留给阶段 3，由本文的架构不变量与模块边界来约束。

---

## 一、从灵魂出发：架构不变量

设计文档的核心精神可以沉淀为一组**不可违背的架构不变量**。它们不是功能清单，而是任何实现都必须保持的"形状"。违背任何一条，产品就会偏离最初的灵魂。

| # | 不变量 | 含义 | 为什么要守住 |
|---|--------|------|--------------|
| I1 | **档案不可变** | 一旦入馆，内容即被保存；变更以"版本/补充"记录，而非静默改写 | 保存"庄严感"，让档案成为一份被认真对待的记录 |
| I2 | **随机先行** | 首要入口是"随机遇见"，而不是搜索、榜单、推荐 | 这是区别于媒体门户与信息流的唯一支点 |
| I3 | **普通即价值** | 不排序、不加星、不比热度；每份档案规格相同 | 系统不应优化"有趣"，而应保存"存在" |
| I4 | **内容即档案** | 一份采访的正文由一组**结构化的单元**组成，其他一切视图都是它的投影 | 单一事实来源，避免三视图各自为政、数据漂移 |
| I5 | **相遇无终点** | 档案随人和时间成长：追问、补充、多年后回访、未答之问 | 档案是活的生命记录，不是发布即封存的文章 |
| I6 | **克制** | 任何新增机制都必须由灵魂来辩护，而非由流量/功能驱动 | 防止滑向"展示人的互联网" |

> 一句话：**系统为"保存"服务，不为"分发"或"攀比"服务。**

## 二、领域拆解（统一语言）

在动手之前，先把世界里的名词钉死。它们构成整个系统的**统一语言**，后续所有模块、数据与界面都围绕它们说话。

| 概念 | 定义 | 关键边界 |
|------|------|----------|
| **人 Person** | 被采访过的主体 | 不是"账号/粉丝"，而是可随时间多次被采访的"存在"；拥有自己的档案线与时间线 |
| **档案 Archive** | 一个永久的、编号的、庄严的记录单元 | 保存"一个人曾经来过"的最小尊严单位；一个人可有多份档案（不同时期） |
| **采访 Interview** | 一次具体的相遇会话 | 属于某份档案；有编号、日期、时长、参与者；是一个人时间线中的一节 |
| **单元 Unit** | 采访的最小原子片段：问题、回答、图片、沉默、备注、小节 | 有序、带时间戳；可指向"它由哪一句引出"（parent）；是内容唯一的真相源 |
| **问题 Question** | 一种单元 | 可作"原计划的问题"或"实际问出的问题"；是问题关系图的节点 |
| **话题 Topic** | 跨档案的标签 | 连接人与采访，是漫游与时间旅行的锚点之一 |
| **时间 Time** | 一等的公民 | 既是采访内部的钟（停顿、沉默），也是档案的年代维度（可回望某一年） |
| **互动 Interaction** | 附属于内容的注释/提问/引用/记忆 | 是"与档案对话"，不是围绕人形成的新流量竞争 |

> 领域三要素：**人写下了什么（单元） → 构成了什么（采访） → 被保存成什么（档案）。**
> 其余都是关于"如何被发现、被理解、被再次遇见"的工具。

## 三、核心体验 → 能力模块

把设计文档中的体验映射成**职责清晰的模块**。每个模块只回答一个问题，边界不重叠。

| 模块 | 职责 | 服务的关键词 |
|------|------|--------------|
| **漂流瓶 Drift** | 从档案馆提供一个"可随机遇见的相遇" | 随机、偶然、平等 |
| **档案视图 Archive View** | 对同一份单元流作出三种投影：故事 / 对话 / 档案 | 庄严、真实 |
| **时间线 Timeline** | 呈现采访内部的钟——包括沉默与停顿 | 真实、温暖 |
| **问题关系 Question Graph** | 展现"哪一句引出哪一句"，可溯源可回看 | 真实、偶然 |
| **漫游 Rabbit Hole** | 跨人 / 话题 / 问题 / 采访 / 年代的开放导航 | 平等、偶然 |
| **时间旅行 Time Travel** | 按年代回望档案馆 | 纪念、见证 |
| **社区互动 Community** | 注释 / 提问 / 引用 / 记忆，可见性可控、需受约束 | 温暖、庄严 |
| **落档 Publishing** | 从原始采访 → 结构化单元 → 入馆的编辑管线 | 庄严、仪式感 |

> 设计要点：**Drift 与 Archive View 是"核"**，其他模块都是围绕它的"边缘"。它们的优先逻辑由下文的阶段决定。

## 四、分解为可行的开发方案

### 4.1 依赖方向

模块之间存在明确的、单向的依赖链，保证了系统的稳定性与可替换性：

```
        ┌────────────────────────────────────────┐
        │  领域核心（单元 · 采访 · 档案 · 人）       │   ← 单一真相源，其他一切建立其上
        └───────────────────┬────────────────────┘
                            │
        ┌───────────────────┼────────────────────┐
        │                   │                    │
  ┌─────▼─────┐      ┌─────▼──────┐      ┌───────▼──────┐
  │ 档案视图    │      │  漂流瓶     │      │  落档(编辑)   │
  │ 三视图投影  │      │  随机发现    │      │  原始→结构化  │
  └───────────┘      └────────────┘      └──────────────┘
                            │
        ┌───────────────────┼────────────────────┐
        │                   │                    │
  ┌─────▼─────┐      ┌─────▼──────┐      ┌───────▼──────┐
  │ 时间线     │      │  问题关系    │      │  漫游·时间旅行 │
  │ 采访内部钟 │      │  溯源回看    │      │  跨档案导航    │
  └───────────┘      └────────────┘      └───────┬──────┘
                                                 │
                                     ┌──────────▼──────────┐
                                     │  社区互动（附属于内容）│
                                     └─────────────────────┘
```

原则：**领域核心只依赖统一语言；边缘模块只依赖领域核心；社区互动只附着于内容，绝不反过来定义内容。**

### 4.2 阶段划分（每阶段有可验证目标）

自上而下、由核到边，每一阶段都能独立交付、被验证，并且不依赖尚未决定的技术细节。

> **P0 · 立骨架**
> 跑通最小闭环：一次真实采访 → 沉淀为结构化单元 → 以三种视图渲染出一份档案 → 提供一次"漂流"入口。
> **可验证目标：** 一个普通人的采访被完整落档并公开可读，且一个陌生人能通过"漂流"到达它。

> **P1 · 建档案**
> 补齐档案的身份与纵深：人的时间线（多场采访归并）、编号与尊严体系、档案元数据、按年代的时间旅行、话题归类。
> **可验证目标：** 档案馆可增长；任何人、任何一个年代的切片拥有完全相同规格的庄重呈现。

> **P2 · 漫游与社区**
> 展开关系与参与：问题关系图、跨档案的兔子洞导航、注释 / 提问 / 引用 / 记忆（带可见性与引导约束）。
> **可验证目标：** 用户可在漫无目的地行走中自然继续，并在不引入点赞 / 粉丝 / 排行榜的前提下留下痕迹。

> **P3 · 成长与持续**
> 让档案随人成长：未答之问、后续回访、多年后的再次采访、内容版本化演进。
> **可验证目标：** 档案不随发布而冻结，而是随一个人的生命持续生长。

> 阶段依赖：P0 先行（核），P1 撑起纵深，P2 赋予漫游与参与，P3 交付"无终点"。**每一步都由 I1–I6 校验：若某机制违背不变量，则不做。**

## 五、明确留白（留给阶段 3）

为避免被实现细节绑架，以下事项**现在不做决定、也不讨论**，仅在阶段 3 按本文的架构不变量去选型：

- **技术栈 / 框架**：如何构建领域核心与各模块
- **部署形态**：如何托管服务
- **数据与存储**：单元、采访、档案如何落盘，如何支持随机发现与时间维度
- **检索与全文本**：如何支持话题、年代与问题关系的寻找
- **实时 / 协同**：采访是"现场采集"还是"录后落档"，是否需要在场
- **身份 / 权限**：编辑者、受访者、社区参与者的边界

> 这些决定**必须服务于 I1–I6**，而不是反过来决定产品形状。它们将在阶段 3 以"架构不变量为约束、以 P0–P3 为节奏"的方式逐一落地。
